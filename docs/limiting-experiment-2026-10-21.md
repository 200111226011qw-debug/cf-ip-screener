# 限流类型实验报告（2026-10-21）

判定 CF 的 429 属于**窗口型**（限请求数/速率）、**字节型**（限流量）还是
**累计型**（总配额）。

## 实验设计

同一台 CI runner（美西 vantage）、同一时段连续跑，候选池、连通性阶段、
并发模型一致；只有「体量 / 并发 / 发起速率」按组变化。

| 组 | 单请求体量 | 并发 | 发起速率 | 候选数 | 轮数 |
| --- | --- | --- | --- | --- | --- |
| (a) 基线 | 10MB | 8 | 不限（实测 ~73 req/s） | 300 | 3 |
| (b) 限速降并发 | 10MB | 2 | 2 req/s | 150 | 1 |
| (c) 小体量 | 256KB | 8 | 不限（实测 ~15 req/s） | 150 | 1 |
| (d) 小体量 + 生产默认 | 256KB | 8 | 不限 | 300 | 3 |
| (e) 新默认配置（验证用） | 256KB | 8 | 不限 | 300 | 3 |
| (f) 1MB + 限速 | 1MB | 8 | 4 req/s | 300 | 3 |

## 结论：**字节型**（且速率是次要因素）

1. **429 由「单请求体量」主导**：10MB 的请求无论发起多慢都会被限——(b) 已经
   压到 2 req/s + 并发 2，仍然 46% 被限；256KB 的请求在两个**不同出口 IP**
   上都是 0% 被限（(c) 124 个、(d) 300 个，合计 424 次请求 0 次 429）。
2. **发起速率是次要因素**：同样 10MB，(a) ~73 req/s → 85% 被限，
   (b) 2 req/s → 46% 被限。限速能把 429 砍掉一半，但**消不掉**。
3. **不是并发维度**：(b) 把并发压到 2、在飞峰值实测 2，仍有 46% 429；
   (c)/(d) 并发 8、峰值 8，429 却是 0。
4. **不是累计配额**：(d) 一轮 300 个请求 + 两轮复测共 ~900 次请求、230MB，
   全程没有出现「一开始正常、后来全被拒」的形态。
5. **限速器本身工作正常**：(b) 的在飞下载峰值 = 2 = 并发上限，
   124 个请求耗时 109s ≈ 124/2 req/s，与 2 req/s 的设定吻合。
   峰值是「限速器是否生效 / 429 是否由并发触发」的关键判据——(b) 峰值 2 而
   429 仍在，直接排除了并发维度。

### 结论的边界（必须标注的混淆）

- **「速率是次要因素」这条带混淆**：(a) 85% 与 (b) 46% 的差异里，**有多少
  来自发起速率、有多少来自出口 IP，分不清**——(a) 的出口 IP 当时还没记录
  （`cf-meta-ip` 埋点晚于 (a)），(b) 用的是另一个出口。引用这条时要带上
  这个限定。
- **主结论不依赖单一出口**：(c)(d)(e) 用了**三个不同出口 IP**
  （130.131.202.46 / 48.217.147.133 / 192.9.250.241），合计 707 次请求
  **0 次 429**——这排除了「出口特异性」，比单出口严格对照更稳。
- **不是累计配额**：(d)/(e) 一轮 300 个请求 + 两轮复测共 ~900 次请求、
  230MB，全程没有出现「一开始正常、后来全被拒」的形态。

## 落地决策

- **默认 `speed_url` 改为 256KB**（`__down?bytes=262144`）：429 归零，
  测速阶段 18s 跑完 300 候选 × 3 轮，产出 50 条纯净。
- **共识口径不改**：3 轮共识只剔了 9/294（3%），产出 50/50 good。
  「复测轮只判 200 + colo 一致 + 收满、速度只用首轮」这套改动**不需要**
  ——256KB 的速度测量够稳，噪声没到误杀的程度。
- **10MB 保留为可选**（想测长连接吞吐时用），但必须配合
  `--speed-rate-limit`（否则 85% 被限）；`speed_rate_limit` / `speed_rate_burst`
  已在 `--speed-rate-limit` / `--speed-rate-burst` 暴露。

## 429 毒化的判定标准（先定，避免下轮再讨论一轮）

**但 g3 的数据已经回答了这个问题（该样本下）：不存在 429 毒化。**

g3 轮同一批 300 个候选跑了**两遍**（先 256KB 主口径，再 10MB 对照口径，
中间隔了 5 分钟）：

- 主口径（256KB，先跑）的 15 个 403：`172.65.168.207 172.65.42.150
  172.65.207.238 172.65.206.58 172.65.248.81 172.65.34.113 172.65.244.192
  172.65.162.54 141.101.90.23 172.65.38.22 172.65.253.248 172.65.172.72
  172.65.51.170 172.65.46.229 172.65.193.135`
- 对照口径（10MB，后跑）的 403：`172.65.168.207 172.65.244.192
  141.101.90.23 172.65.253.248 172.65.193.135` ← **5 个与主口径的 403 重合**
- 对照口径的 429 列表里含 `172.65.42.150` ← 主口径 403 的 IP 在后跑的那遍
  变成了 429

**判读**：主口径的 403 发生在**前**（256KB 那遍，没有任何 429），而且 5 个
IP 在后跑的那遍**仍然是 403**——所以 403 是**该 IP/网段自身的信誉属性**，
**不是 429 的副作用**。一个被 429 的 IP 在下一轮变成 403 这件事，在本样本里
没有发生。

判据仍先定好（供将来数据用）：取**上一轮被 429 的 IP 集合**与**本轮被 403
（或再次 429）的 IP 集合**的交集，除以上一轮 429 的总数。

| 交集占比 | 判定 | 处置 |
| --- | --- | --- |
| 0 – <5% | 限流是**瞬时**的，每轮独立 | 不需要冷却期，当前行为即可 |
| 5% – 20% | **轻度持续** | 建议：上一轮被 429 的 IP 在下一轮降优先级（排到测速候选末尾） |
| >20% | **重度持续**，候选池会被逐渐毒化 | 需要：轮换候选池，或引入按 IP 的冷却期 |

配套埋点已就位：每轮记录 429/403 的 IP 明细（主侧与对照侧都记）。

## 403 采样（进行中）：先弄清「403 是什么」，再谈要不要动网段

**当前状态：只做采样诊断，不做任何网段过滤。** `172.65.0.0/16` 的 `[warn]`
保留、不排除——在证据出来之前，这是唯一正确的状态。

### 为什么不能先排除网段

403 集中在某个 /16 是**相关性**，不是因果。两种完全不同的解释：

- **(a) 探针盲区**：该 IP/网段对**普通 CF 域名**其实完全可用，只是
  `speed.cloudflare.com` 这个端点不服务它（某些 CF 边缘的 WAF 规则、
  特定 IP 段的策略等）。→ 排除它就**错了**，会把对订阅者真正可用的节点
  排掉。
- **(b) 真的被拒**：该 IP/网段被 CF 的 access rule 拒绝（error code 1020）。
  → 这时才考虑网段过滤。

**先排除再问「403 是什么」，顺序是错的。**

### 采样字段（每轮最多 5 条 403，零行为变更）

| 字段 | 用途 |
| --- | --- |
| `server` 头 | 区分 `cloudflare` / 其它（反代/中间层） |
| `cf-mitigated` 头 | `challenge` / `block`（Cloudflare 的 WAF 挑战标记） |
| 响应体前 100 字节 | CF 错误页的 error code：**1020** access denied、**1015** rate limited、**1006** IP banned… |
| 请求的 Host | 确认打的是 `speed.cloudflare.com`（不是别的） |

**响应体里的 error code 比 `server` / `cf-mitigated` 更直接**——探针盲区不会有
1020 这种码。

### 判读矩阵

| 测速端点 | 普通/自定义域名 | 结论 | 处置 |
| --- | --- | --- | --- |
| 403 | 200 | 探针盲区，IP 对普通 CF 域名可用 | **不排除网段**；考虑换测速端点或 Host |
| 403 | 403 | 该 IP/网段确实被拒 | 才考虑网段过滤（仍需 1020 佐证） |
| 403 + `cf-mitigated: challenge` | — | WAF 挑战（bot 检测） | 降优先级，不是永久排除 |
| 403 + error code 1020 | — | 该网段被 access rule 拒 | 才考虑网段过滤 |

### 将来真要做动态网段信誉，两个必须解决的前提

> **本方向已关闭**：403 的成因是「Host 不被该 IP 服务」（探针盲区），不是网段
> 信誉——前提不存在了。下面三条作为**历史记录**保留（若将来出现真正的
> 网段级封禁迹象，再按这三条做）。

1. **解除不能靠「缺席」**：被跳过的 /16 不再产生 403 数据，于是
   「连续 2 轮不满足」在**无观测**中自动成立 → 每约 3 轮标记一次又解除，
   必然震荡。必须留**金丝雀**（每轮放行 ≤3 个）且**只在观测到 200 时**解除。
2. **状态不能塞进现有提交路径**：`.ci-state.json` 现在只存 `empty_streak`，
   加了网段状态后每次变化都是一次提交，而提交信息「ci: 空结果连击计数 N」
   会误导。要么改提交信息模板，要么把网段状态放到别处。
3. **过滤位置在 `speed_cap` 之前**（不是连通性阶段之前）——即：先把候选按
   延迟排序、再截断到 `speed_max_candidates`，网段过滤若要做应作用在
   「进入测速的候选」这一层。

**读出来的三件事**：

第 3 点很关键：**判读矩阵里最直接的那条证据（error code 1020 = 网段被 access
rule 拒）并不成立** —— 没有 error code 就没有这条证据。

  `speed.cloudflare.com` 这个专用 hostname 在一部分 CF 边缘上没有配置，
  对它返回 403，但对普通 hostname 正常服务。

### 由此产生的一个更根本的问题（已定性，并已用轻量方案处理）

**403 是测速里的「假阴性」**：这些边缘本身可能是好节点，但我们的探针
（`speed.cloudflare.com/__down`）测不到它们，于是被当作失败剔除。

**范围是全局的，不只 172.65 一族**：抽样里 `141.101.90.23`（在 172.65 之外）
也是同一机制。而更根本地说：

- `speed.cloudflare.com/__down` 测的是「这个 IP 是否服务**这个特定 Host** 的
  下载端点」；订阅者用的是**普通 CF 域名或自己的域名**，不是
  `speed.cloudflare.com`；
- 所以测速漏斗测的是「**探针可达性**」，不是「**订阅者可用性**」。这个偏差
  一直存在，只是 403 把它显性化了——**每一轮的每一个 403 都是一个假阴性**
  （实测每轮 7–18 个候选，300 的 2–6%）；
- **换探针 Host 解决不了这个问题**：`www.cloudflare.com` 上没有
  `__down?bytes=` 这种可控体量的下载端点，256KB 测速方法不成立。换 Host
  实际是**换测速方法**（要重新设计端点、重新标定 `speed_scale`、重新验证
  限流行为）——成本与风险都高，**不做主路径**。

#### 采用的轻量方案：403 二次验证（不改主漏斗语义）

对 403 的候选再打一次**普通 CF 域名**：

- 200 → 标记 `probe_blind`（域名可达、测速端点不可达、**速度未知**），
  回收进结果；
- 其它/失败 → 维持原判（真不可用）。

而且**安全网在健康期就已经有贡献了**：回收 13 个、最终保留 **1 个**

- 盲区候选的延迟与产出**基本持平**（2.2 vs 2.0ms）→ 它们**在健康期就有
  竞争力**。之前「M 恒为 0」是那几轮的池构成不同（回收数 8 / 8 / 36 / 14 的

- **回收数确实是波动指标**（8 → 8 → 36 → 14），印证「池里盲区候选数 ×
  该 runner 落到的边缘的 403 概率」这个双因素。

**留下的判断**：延迟中位持平、且已观察到 M=1，「留名额」的价值是**在池变薄 /
top_n 截断边界附近多留几条**。具体形态（固定比例 vs 只在 M 不足时补位）可以
再定，但**默认不截断盲区候选**这个方向已由数据支持。

**403 与 TLS/连接层失败是两类**（例：`172.65.168.207` 两次都是 TLS 握手
EOF，不是 403）——只有 403 进二次验证，连接层失败不混进「假阴性」。

可行性核对（**结论：可行**）：速度缺失（`speed_mbps = None`）在整条链路上
只有 `filter.py` 的速度比较不是 None-safe（`None < 0` 会抛 TypeError），
已修为 `(r.get("speed_mbps") or 0.0) < min_speed_mbps`；其余
（`output.py` 的备注、`report.py` 的速度分布、`score.py` 的「None = 没跑测速，
不扣不加」）本来就按「速度未知」处理。

- `speed_mbps` 记 **None**（**不是 0**）：0 表示「测出来是 0MB/s」，
  None 表示「没测到」。下游据此区别对待。
- 排序键不变（`(loss_rate, avg_ms)`）——它们本来就不靠速度排序；
- 备注加标记「域名可达(无速度数据)」，免得被误读成「慢节点」；
- 报告漏斗注明「含 N 条域名可达但无速度数据」；
- **代价要说清**：这些节点**没有速度数据**，无法参与速度排序，也无法验证
  带宽。`speed_blind_output` 开关：main（默认，进主结果）/ separate（只记数
  不加入）/ off（不做二次验证）——若数据显示它们挤占了有速度数据的节点，
  一键切到 separate 即可回退。

### 盲区保底名额：落地与端到端验证（2026-10-21 19:41 UTC）

#### 为什么重构会改错（下次怎么避免）

审计表只回答了「这次没问题」，没回答「为什么会错」。事实是：

- **正确的写法一直存在**（前三个 commit 都是 `_a ← r1, _b ← _cres`），
  不是从零设计时写错的；
- 错误是在**重构 `_aligned_map`** 时引入的 —— 把「两行 zip」合并成「一步构造」
  时，顺手把 `_a` 的来源从 `r1` 改成了 `_cmap`。**两段看起来对称的代码，
  合并时最容易把「来源」改错。**

已落成结构性约束（不只写进文档）：

- 「两个来源」写进函数签名：`compare_dual_body(primary_map, compare_map)`
  ——两个参数名直接说明各自是什么；
- **传入同一个对象直接报错**（`primary_map is compare_map` → ValueError），
  「自比自」这种失效模式在结构上不再可能悄悄发生；
- 有测试锁死（`tests/test_speed_compare.py::DualBodySourceGuardTest`）。

> 教训：**重构涉及「两个来源 / 两条对称路径」的代码时，要在 diff 里显式标注
> 来源，不能靠「看起来对称」来保证。** 对称的代码合并时，最容易悄悄把其中
> 一边的来源换掉，而日志看上去完全正常。

### watch 模式下的行为

`--watch` 循环**不捕获** `run_once` 的异常 —— 与批量模式一致：

- **轮次级失败**（空结果守卫）走 `return 3`，**不是异常** → watch 照常进入
  下一轮 ✓；
- **编程级错误**（对齐契约破坏 → RuntimeError）→ **整轮崩、watch 进程退出**。
  理由与批量模式相同：错位意味着本轮产出整体不可信；让一个坏路径在 watch
  循环里每小时空转一轮，比立刻退出更糟（操作者不会发现）。

**「编程错误」与「数据异常」在代码里是同一个 RuntimeError** —— 两者都触发
「产出不可信 → 退出」。数据异常（某个池返回了畸形数据导致长度对不上）确实
不该静默继续，所以**当前处理不偏**；但 watch 长期运行时，操作者需要能
判断「是不是改代码改坏了」还是「池子抽风了」。故错误日志里直接列出两种
可能原因：

```
[ERROR] 可能原因：① 代码改动破坏了「结果与候选等长」的契约（改代码后重跑）；
        ② 候选池返回了异常数据（数据问题，下一轮可能自行恢复）。
        本轮已终止，不会提交结果。
```

（真正的分类需要更多上下文——比如比对 `st.run` 的入参与返回值——属于未来
优化。当前至少让操作者知道有哪两种可能、且本轮不会提交结果。）

## 1MB 跨出口验证的可执行方案

1MB 只有单出口验证过（(f) 组，1MB @ ~17 req/s → 429=0），而 10MB 在不同出口
的限流差异很大（(b) 46% vs (g2) 88%）——所以**限流阈值本身随出口波动**，
1MB 必须跨出口验证才能切。

方案（不阻塞当前默认配置）：

1. 在 Actions 里手动 dispatch **3 次**，每次间隔 **≥1 小时**（避免同一台
   runner / 同一出口）；
2. 每组：300 候选 × 3 轮，`extra_args` 填
   `--speed-url https://speed.cloudflare.com/__down?bytes=1048576 --speed-rate-limit 4`；
3. 每组记录：**出口 IP**、首轮 429 比例、纯净数、测速阶段耗时；
4. 判定：**三个出口的 429 比例都 = 0 → 可以切**；**任一出口 >5% → 保持 256KB**。

## 压测交付的是「可用但质量数据不完整」的节点

35 条全输出，意味着危机时上游拿到的是 35 条**无速度数据**的节点（`speed_mbps`
为 null、备注带「域名可达(无速度数据)」）。这是安全网的**预期行为**，但要点明：

> **危机时交付的是「可用但质量数据不完整」的节点，不是「完整质量」的节点。**
> 订阅者如果依赖速度排序，这 35 条对他们来说只是「能连上」，不是「优选」。

## 三档判据的第一档需要**健康期**数据，压测数据不能替代

压测那轮 35 条全进输出，是因为**主漏斗崩溃 + 候选总数 36 < top_n=50，没有
截断**。这不代表健康期也能全进——健康期 `top_n` 会截断，**延迟中位差才是
决定因素**。

> 压测只能回答「**危机时能不能交付**」，**不能**回答「**健康期能不能竞争**」。
> 三档判据的第一档（差 <10ms）需要健康期的数据。
> 看到「压测 35 条全进」就以为盲区候选在健康期也能全进，是误读。

## 关键路径的日志：打「实际生效数」，不是「意图数」

回收逻辑错位时，**意图数与实际数完全一致**（都是 35），只有实际数才能暴露
「找到了但没加进去」。现在两行分开打：

```
探针盲区候选：回收 35 个，实际加入结果 35 个
```

并且加了**不变量检查**：回收的候选都通过了连通性筛选 → 必然能在共识前的行里
找到 → 实际加入数应等于回收数；对不上就 `[ERROR]` 报警。这样这类 bug 不必等
压测才暴露 —— **安全网类机制平时不触发，触发了才发现是坏的**，所以关键路径
要能自己报警。

压测若不隔离「上一轮结果复用」（v2.2.0 的旧节点重筛，会把上一轮
`clean-ips.json` 里的 IP 并进候选池），主漏斗照样满血，测不出安全网的真实
行为。**压测的隔离条件已固化成 `scripts/stress_blind_spot.sh`**（含三个隔离
条件与自动判读），详见 `docs/blind-stress.md`。

## 压测脚本的判据（三态）

`scripts/stress_blind_spot.sh` 自动判读，**INVALID 的定义是「压测前提不成立」**
（**不是**「结果全进了」——候选数少、没有截断是压测的正常形态）：

| 判定 | 条件 |
| --- | --- |
| **INVALID** | ① 主漏斗没 100% 崩溃（存在任何非 403 响应 → 主路径没饿死）；② 状态码计数 **>** 测速候选（日志重复计数，真不自洽）；③ 测速候选数 ≥ top_n（存在截断可能，「全都进了」说明不了任何事） |
| **BROKEN** | 前提成立但安全网没起作用：没有「实际加入结果」行 / 实际加入数 ≠ 回收数（不变量被破坏）/ 回收了但一条都没留下 |
| **OK** | 前提成立且安全网交付了非空结果 |

**条件 ② 的方向要分清**（容易搞反）：状态码计数 **<** 测速候选 = 有候选没走到
HTTP 层（超时 / 连接失败 / TLS 失败）——这是**正常**的（压测注入的 IP 混有连接层
失败很常见），只作 `[info]` 提示，**不判 INVALID**；只有 **>** 才是重复计数。
（这个提示必须**独立于判定链**，放成 elif 会把后面的分支整条吞掉。）

**不变量检查的统计点**（`main.py`）：比的是「**加入回收列表后立即的长度**」
（`_added`），**不是**最终输出里的数量（`_blind_final`）——后者会被共识剔除 /
min_speed 门槛 / top_n 截断压下去，M<N 是正常的，拿它做不变量会变成假警报。
两个数在代码里是**两个不同的变量**，注释也写明了。

`_added` 的前提是回收列表**没有重复行**：`forbidden_candidates()` 自己按
`(ip, port)` 去重（不依赖上游候选池已去重这个不变式）——否则重复候选会让
`_added` 多算 → 不变量误报 BROKEN。同 IP 不同端口是**不同**候选，保留。

**对齐契约也显式化了**：`forbidden_candidates()` 要求 `all_keys` 与 `results`
**等长且按位置对齐**，长度不等直接抛错（不是让 `zip` 静默截断）——截断会让
后半段候选压根进不了列表，回收漏掉它们，而**不变量检查不会报警**（N 与 M 同时
变小、仍然相等）。

**对齐破��时的语义：整轮崩掉**（不是「记日志、跳过回收、主漏斗继续」）。
理由比「安全网坏了不该拖垮主漏斗」更强一层：错位意味着「**哪个候选对应哪个
测速结果**」不再可信 → 速度归属、共识、最终名单**全都可能配错** → 本轮产出
整体不可信。记条日志继续跑，产出的是一个**看起来正常、实则可能配错**的结果 ——
那正是这个项目一直在消灭的静默降级。

- **主检查**（调用点，带运行上下文）：`main.py` 的 `_aligned_map(keys, results,
  what)` → 记 `[ERROR]` 后 **raise RuntimeError**。**检查与映射构造合成一步**，
  映射只可能在对齐通过后被造出来 → 「先建映射、后检查」的顺序错误不可能发生
  （顺序由代码保证，不靠注释声称）。
- **兜底**（`forbidden_candidates()` 内部）：同样 **RuntimeError**，供其它调用方。
  两处语义一致，不存在「一处抛错、一处记日志」的分裂。
- **CI 侧配套**：「提交结果」步骤显式写 `if: success()` —— 失败轮（空结果守卫
  退出码 3、对齐契约 RuntimeError 退出码 1、其它异常）**一律不提交**。
  失败轮的 result/ 可能是空的、也可能是配错的坏数据，**提交上去比不提交更糟**。
  GitHub Actions 默认就是「前序失败则跳过」，但那是隐式的 —— 把上面 artifact
  步骤的 `if: always()` 照抄过来就会破功。`tests/test_ci_wiring.py` 锁住这条
  （提交步骤必须是 `success()`、artifact 必须是 `always()`、运行步骤必须用
  `PIPESTATUS` 传出退出码）。

#### ⚠️ 待修：状态文件的 push 失败是**静默**的（与「空结果覆盖好结果」同类）

事实（2026-10-22 核过 `.github/workflows/auto-run.yml`）：

| 步骤 | push 方式 | 重试 | rebase | 失败表现 |
| --- | --- | --- | --- | --- |
| 提交结果 | `git pull --rebase --autostash -X ours && git push` | **3 次** ✓ | 有 ✓ | 3 次都失败才报错 |
| 空结果连击与告警（状态文件） | `git push` | **无** ✗ | **无** ✗ | `|| echo "状态文件 push 失败（不影响告警）"` → **静默** |

**为什么值得未来修（不是「已知事实」，是带着标签的待修项）**：

- 这是**静默失败**——和「空结果覆盖好结果」同一类：没有报错、没有红灯，
  只有「某个本该被记住的状态没被记住」。
- **最需要它的场景恰好最依赖它**：空结果轮 → run 失败 → 「提交结果」被跳过
  → 状态文件是**唯一**把失败记下来的通道，而它恰好是最脆弱的那个
  （无重试、无 rebase、失败静默）。
- **「远端前进 → 非快进 push 被拒」比瞬断更常见**：CI 检出后只要远端动了
  （例如有人推了文档），`git push` 就被拒 → 状态文件这一轮没落库 → **连击数
  少算** → 告警可能晚一轮才发，甚至不发。
- 2026-10-21/22 已实际观察到 `github.com:443` 反复瞬断（同机 `api.github.com`
  正常）→ 无重试的 push 正好撞上这个窗口。

**修法很小**（同一个 3 行区域）：把状态文件的 push 换成与「提交结果」同款
的 `for i in 1 2 3; do git pull --rebase --autostash && git push && break; sleep 3; done`。
**现在不改**——网络瞬断不是仓库问题，且这段逻辑在 CI 里改动的风险高于收益；
等瞬断变成常态、或连击告警真的漏发过，再动。

## 回收列表的来源：只有 403 二次验证**通过**的

`forbidden_candidates()`（`screener/speedtest.py`）按

## 压力测试：安全网在主漏斗崩溃时能不能顶上（2026-10-21 15:21）

健康期 M=0 是正常的，**不能据此判断安全网有效或无效**。真正的测试是「主漏斗
崩溃时安全网能不能顶上」——压力期不会主动出现，所以**手工构造**。

### 构造方法

用 `--pool` 注入一份**只含盲区候选**（172.65.0.0/16 里被 403 的那些 IP）的
列表（`docs/blind-stress-ips.txt`，36 个，2026-10-21 快照），并用
`--outdir` 指向一个**空目录**。

⚠️ 两个必须注意的坑（都踩过）：

1. **「上一轮结果复用」会把主漏斗填满**：流水线会把上一轮的 `clean-ips.json`
   里的 50 个 IP 也并进候选池重筛（v2.2.0 的「旧节点自动重筛」）。第一次
   压测就因此「主漏斗没被饿死」——36 + 上一轮 50 = 86 个候选，主路径照样产出
   50 条。**必须用 `--outdir` 指向空目录**才能隔离它（上一轮结果从
   `output_dir/clean-ips.json` 读）。
2. **`--pool` 是替换默认池**，但官方段不在池里（它们只用于段校验），所以池子
   确实只有注入的那 36 个。

### 结果（修复后）

```
去重后共 36 个候选              ← 上一轮复用已被隔离，主漏斗真的被饿死
首轮 HTTP 状态码：403×36         ← 主漏斗 100% 被 403
首轮失败归因：forbidden 36
探针盲区回收 35/36 个
探针盲区候选：回收 35 个，实际加入结果 35 个
候选总数: 36  已测试: 36  测速候选: 36  纯净可用: 35   ← 输出非空
探针盲区：回收 35 个 → 最终保留 35 个
```

**结论：主漏斗 100% 崩溃时，安全网交付了 35 条纯净 IP，输出非空 → 可用。**

### 压测暴露的一个真 bug（安全网一直是空转）

第一次压测（修复前）：

```
探针盲区回收 35/36 个
探针盲区候选 35 条进入结果      ← ★ 日志说 35 条进入结果
候选总数: 36 ... 纯净可用: 0    ← ★ 实际 0 条
```

**回收逻辑找错了列表**：盲区候选（403 → 速度 0）**从来没进过共识**（共识里
没有它们），而回收时却在**共识幸存者**里找它们 → 一条都找不到 → **安全网
全程空转，却一直打「35 条进入结果」的日志**。日志打的是回收数
（`len(_blind)`）而不是实际加入数，掩盖了这一点。

修法：① 保留**共识前**的行（带 avg_ms/loss_rate/tls_ok 的原始行）作为查找
对象；② 日志改打**实际加入数**。

**这个 bug 只有压力测试能暴露** —— 健康期 M 恒为 0，无论回收逻辑对不对，
输出都一样。

### 回收数波动的两个来源（回收数不是稳定指标）

```
回收数 = 池里盲区候选数 × 该 runner 落到的边缘的 403 概率
```

- **池构成**：某 /16 的候选数变多（13:36 那轮池里 172.65.0.0/16 有 40 个，
  前两轮约 8 个）→ 回收数随之涨。**下一轮如果回收数又掉回 8，不要当成
  「盲区缩小」，只是池构成回来了。**
- **runner 落到的边缘**：同一条 IP 在不同边缘的 403 概率不同。压测这轮 colo
  几乎全是 **IAD**（runner 本地边缘），而 13:36 那轮是 MSP/AMS 为主 —— 边缘
  确实在变。colo 自检在 36 次里报了 2~3 次「两次落到不同边缘」。

所以**判据表里的「回收数 ≥20」是波动的，可能误触发**；它只能作为「去看一眼
403 网段分布」的信号，不能单独作为「留名额」的依据。

## 判读判据（先定好，数据回来直接对号入座）

日志会给出「回收 N 个 / 最终保留 M 个」+ 两组的延迟中位与 score 中位。
**判据（先定，避免数据回来再讨论一轮）**：

| 观察到的模式 | 判定 | 处置 |
| --- | --- | --- |
| **连续 3 轮 M=0** 且回收数稳定（7–18） | 安全网只在极端情况（候选池骤降）才生效 | **接受这个定位，不调**。这是设计意图 |
| **连续 3 轮 M=0** 且回收数 ≥20 | 探针盲区在扩大，安全网永远顶不上 | 触发「给盲区候选留名额」的讨论（例如 top_n 里划 10% 给它们）——**判据在此，数据一到即执行** |
| M 偶尔 >0，回收数稳定 | 安全网按预期工作 | 不调 |
| **M 偶尔 >0，但回收数在涨**（如 7 → 25） | 盲区在扩大，**尚未**到「永远顶不上」的程度 | **加观察标记、看趋势**：不立即调，但按轮记录回收数；等它越过 20 这条线再按上一行处理 |
| **M 连续为 0，且回收数单轮跳升到 ≥20**（首轮出现，见下） | 盲区在扩大，但**膨胀来自候选池构成**（某 /16 的候选数变多），不是 CF 侧行为变化 | 触发「给盲区候选留名额」的讨论；**先确认膨胀来源**（看「403 网段分布」那一行）再决定 |

**阈值 20 的来源**：历史观测的 403 候选数是 **7–18**（跨 6 轮、多个出口），
20 = **历史最大值 18 + 2 的余量**，即「超过历史波动上限」。这个基准是**移动的**
——随着新轮次进来，历史最大值可能上移，阈值也应随之复核（若某轮回收数
刷新到 25 以上，20 这条线就失去意义了，应按新基准重设）。

### 盲区配额的下一轮判据（新增维度：**被挤掉的普通候选**）

配额的启用条件是「延迟差 ≤ 10ms」，自动关闭是「连续 2 轮延迟差 > 30ms」。
**注意这两个阈值的作用不同**（这一点先前写得不准，已更正）：

- **10–30ms 区间：配额本轮就「未启用」**——启用条件不满足，quota 不生效，
  但也**没有被永久关掉**（自动关闭只认「连续 2 轮 >30ms」）。所以这个区间
  里**没有成本侧数据可看**（配额没挤占任何人）。
- **≤10ms 区间（配额生效）：才是成本侧信号有意义的地方**。聚合上「≈持平」
  说的是**中位数**，而**边际上**被挤掉的那几个普通候选可能仍然明显更好
  （比如被挤掉的是 1ms 的、入选盲区是 6ms，但产出的中位数被一堆 5ms 的
  候选拉住了）→ 聚合判据会漏掉这个。

**这个维度现在每轮可见**（配额启用时打一行）：

```
配额挤占：4 个普通候选出局（被挤掉的延迟中位 5.0ms vs 入选盲区候选延迟中位 5.1ms
—— 被挤掉的比入选快 0.1ms（收紧阈值 5ms → 未超出收紧阈值））
```

**符号约定**：`差 = 入选盲区候选延迟中位 − 被挤掉的延迟中位`，**>0 = 被挤掉的
更快（更好）= 配额的代价为正**。与代码里启用阈值用的「盲区 − 产出」方向一致
（正数都表示「盲区更慢」）。日志里**必须写方向**（「快/慢/持平」），不能只给
「±0.1ms」让人猜符号。

**下一轮数据的判读**（先定好，数据回来直接对号入座）：

| 观察到的模式 | 判定 | 处置 |
| --- | --- | --- |
| 延迟差 ≤ 10ms（第一档）**且**成本侧差 ≤ 5ms | 配额的代价可忽略 | 保持 quota=5 |
| 延迟差 ≤ 10ms（第一档）**但**成本侧差 > 5ms | 聚合「≈持平」掩盖了边际代价：被挤掉的是明显更好的候选 | **收紧**：quota 减半 / 只保底 3 个（下一轮起生效） |
| 延迟差 10–30ms | 配额本轮未启用（启用阈值 10ms）→ 无成本侧数据 | 不动；只观察是否反复落在这个区间（若反复，说明启用阈值 10ms 可能偏严） |
| 连续 2 轮延迟差 > 30ms | 前提不成立 | 现有的自动关闭机制接管（配额失效） |
| 被挤掉的普通候选**数量**异常多（远超 quota） | 截断口径有问题 | 查 `apply_blind_quota` 的挤占逻辑 |

**5ms 这个阈值的来源**：**拍的**——但比「明显」可操作（判据要能对号入座，
不能留一个需要每次重新讨论的形容词）。数据回来后若显示 5ms 不合适（太松或
太紧），再调 `blind_quota_displace_diff_ms`。

**看哪一行**（两个信号在不同行上，别盯着不存在的那行）：

| 要看的信号 | 日志行 | 何时出现 |
| --- | --- | --- |
| 成本侧（被挤掉的候选 vs 入选盲区） | `配额挤占：N 个普通候选出局（…超出/未超出收紧阈值…）` | **仅配额启用时**出现。配额没启用时**这行不出现**——是预期行为，不是日志丢了 |
| 启用侧（延迟差 vs 阈值） | `盲区保底名额：启用 quota=5（延迟差 +X ms ≤ 10ms…）` / `盲区保底名额：未启用（延迟差 +X ms 超过启用阈值 10ms）` | **当轮有盲区候选时**出现（三选一：启用 / 未启用-超阈值 / 未启用-自动关闭）。当轮一个盲区候选都没有 → 整行不出现（无从比较） |

**长期观察点（不阻塞，攒够轮次再看）**：若
`未启用（延迟差 … 超过启用阈值 10ms）`（即延迟差落在 **10–30ms**）**连续多轮**
出现，说明**启用阈值 10ms 相对实际分布偏严**，可能需要放宽。这与成本侧信号
无关（那两轮配额根本没挤占任何人），是**启用阈值**本身的问题。**单轮数据不足
以判断「反复」**——先攒轮次，攒够了再讨论要不要动阈值。

**这是与自动关闭相互独立的第二个信号**：自动关闭看的是「盲区 vs 产出」
（收益侧），被挤掉的候选看的是「配额 vs 代价」（代价侧）。两个信号来自不同
角度 → 交叉验证，比只看一个更可靠。

### 首轮应用（2026-10-21 三轮定时任务）

| 轮次（UTC） | 403 数 | 回收 | 最终保留 M | 纯净 | 429 | 在飞峰值 | 403 网段分布 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 00:27 | 8 | 8/8 | **0** | 50 | 0 | 8 | — |
| 07:19 | 8 | 8/8 | **0** | 50 | 0 | 8 | — |
| 13:36 | **36** | **35/36** | **0** | 50 | 0 | 8 | `172.65.0.0/16 35/40(88%)` |

**判读**：

- **M 连续 3 轮为 0** → 安全网至今**一次都没顶上过**（符合「安全网」定位）。
- 回收数从 8 跳到 35 → 触发「回收数 ≥20」那行。**但膨胀来源已查清**：
  `403 网段分布：172.65.0.0/16 35/40(88%)` —— 这轮候选池里该 /16 的候选有

- colo 自检**触发了 2 次**（36 次里约 5%）：两次请求落到了不同边缘

  IP 固有的。这与「该 Host 不被那个边缘服务」的解释一致，且**不影响**
  「该 IP 对普通域名可用」的结论。

**结论**：按判据表，这一轮属于「**回收数单轮跳升到 ≥20**」→ 触发「给盲区
候选留名额」的讨论。但因为膨胀来自候选池构成、且盲区候选的延迟系统性更差
（被 top_n 截掉），**是否留名额应当基于「候选池变薄时的价值」而不是
「回收数的绝对值」** —— 这需要延迟分布数据（下文已补齐该日志）。

配套的两个判读辅助：

- **延迟中位对比**（盲区候选 vs 最终产出）→ 决定「留不留名额」，**三档**：

  | 延迟中位差 | 判定 | 处置 |
  | --- | --- | --- |
  | <10ms（≈ 持平） | 健康期也能竞争 | 留名额，或至少不截断 |
  | 10–30ms（稍差） | 只在池变薄时能顶上 | 留名额但设上限（如 top_n 的 10%），或只在产出 <30 时启用 |
  | >30ms（明显更差） | 健康期永远顶不上 | 接受「安全网只在极端情况生效」，**不留名额** |

  **实测落点：第一档**（健康期 2026-10-21 18:30 那轮，盲区候选延迟中位
  2.2ms vs 产出 2.0ms，差 **0.2ms**）→ **留名额，或至少不截断**。

  注意压测已证明：安全网**在主漏斗崩溃时能交付 35 条**（输出非空）——所以
  「永远顶不上」指的是**健康期**，不是「危机时也顶不上」。
- **score 中位对比**：盲区候选的 score **不含速度项**——None 是**中性锚点**
  （相对最快节点少 15 分、相对中间档少 5~10 分、相对很慢节点**多** 10 分），
  **不是被惩罚**。这个差值不代表质量差，只代表「速度未测」，与有速度数据的
  候选**不可直接比较**。**看这组数时别把它当成质量指标。**

## 403 的网段聚集诊断（已落地）

## 双体量对照（g2）：256KB 会不会改变选品？

**这是「换测速体量会不会改变选品」的唯一干净答案**——必须同批候选、同轮、
同出口。分两次跑做不到（候选池每次重抓、内容会变），故新增
`--speed-compare-url` 模式：同一批 300 个候选，**先**用主口径（256KB）测，
**再**用对照口径（10MB，限速 1 req/s）测一遍同批候选。

结果（出口 IP 141.148.187.195）：

```
对照覆盖：29/300 (10%) 测出速度（其余失败/被限流）
口径 A（主，256KB）10.53 MB/s，口径 B（对照，10MB）93.71 MB/s，绝对比 0.112
相对排序一致性：Spearman ρ=0.326；归一化比值 中位=1.074 区间[0.864, 7.444]
门槛判定（k=0.3×中位数）：A 淘汰 0 / B 淘汰 1 / 判定不一致 1
对照侧失败归因：rate_limited 263 / forbidden 4 / http_error 2 / connect 2
```

### 幸存者偏差：已排除（这是「偏差 ~9 倍」结论的前提）

10MB 对照侧被限流 88%（g2）/ 82%（g3）/ 82%（g4），只有 10–15% 的候选测出
速度。所以「93.71 MB/s 是幸存者偏差后的值」这个担心是对的，**必须验证**。

验证方法：看**幸存者**在**主口径（256KB，无幸存者偏差）**下的速度，是否与
全体候选有系统性差异。主口径的中位数可由自适应门槛反推（`T = 0.3 × 中位数`
→ 中位数 = T/0.3）：

| 轮次 | 出口 IP | 共同样本 | 绝对比 | 共同样本的 256KB 中位 | 全体 256KB 中位 | **幸存者/全体** |
| --- | --- | --- | --- | --- | --- | --- |
| g2 | 141.148.187.195 | 29/300 (10%) | 0.112 | 10.53 | 12.03（T=3.61） | **0.88** |
| g3 | 57.151.129.48 | 44/300 (15%) | 0.133 | 6.25 | 6.20（T=1.86） | **1.01** |
| g4 | 52.242.242.178 | 36/300 (12%) | 0.144 | 14.57 | 15.13（T=4.54） | **0.96** |

**三轮的幸存者/全体比都是 0.88 / 1.01 / 0.96 ≈ 1** → 被限流的候选与没被
限流的候选在**主口径下的快慢没有系统差异**（限流是按请求节奏/总量判的，
与节点本身快慢无关）。所以：

- **绝对比 0.112 / 0.133 / 0.144 是可信的**，不是幸存者偏差的产物；
- 三轮、三个不同出口、三批不同候选给出 0.112/0.133/0.144 —— **偏差稳定在
  7–9 倍**，不是单次巧合；
- 方向上还是**保守**的：幸存者的主口径中位略低于全体（0.88/1.01/0.96），
  意味着 10MB 侧的真实中位可能比记录的**更高**，真实偏差可能 ≥7 倍。

### ⚠️ 这个 7–9 倍的适用范围（不是普适常数）

- **CI 美西 runner（RTT ≈ 2ms）下**：256KB 约为 10MB 的 **1/7 – 1/9**。
- **本地 RTT 高时偏差更大**：实测 ~200ms RTT 下约 **10×**。
- **`speed_scale` 只按体量查表**（256KB → 9.0、1MB → 5.0、10MB → 1.0），
  **本地用默认值会偏保守**（即本地算出的速度分偏严）。本地若要更准，
  需按本地实测 RTT 重新标定这个表。
- 换句话说：7–9 倍是**「CI 美西 vantage + 256KB vs 10MB」这一个条件下的
  测量值**，不是「256KB 相对 10MB 恒定差 9 倍」的定律。

（已落地「幸存者偏差检查」日志行：按 key 比对幸存者/未幸存者的主口径中位。
第一版实现误按结果 dict 比对 → 恒为空 → 静默不打印，已修。）

### 结论

1. **绝对偏差在 CI 上同样是 ~9 倍**（0.112），不是「温和」。我此前说「CI 的
   偏差温和」是**错的**：那是用 (d) 的 256KB 中位 49 与 (b) 的 10MB 中位 123
   跨组比出来的，两组不同批、不同出口、不同时间，不是配对数据。
   **配对数据（同批同轮同出口）给出的答案就是 ~9-11 倍，与链路的 RTT 无关
   ——只要体量小到走不完慢启动，偏差就在这个量级。**
   - **g3 复现**：另一出口（57.151.129.48）、另一批候选 → 绝对比 **0.133**、
     ρ=0.241。**g4 再复现**：第三个出口（52.242.242.178）→ 绝对比 **0.144**、
     ρ=0.675。三轮三个出口 → 绝对比 **0.112 / 0.133 / 0.144**，**稳定在 7–9 倍**。
   - 相对排序的 ρ 三轮分别是 **0.326 / 0.241 / 0.675**（n=29/44/36）——n 太小，
     Spearman 的置信区间很宽，**不能声称排序被保持**，只能说「至多弱到中等
     相关，从未高到能说排序被保留」。
2. **相对排序确实弱相关**（g2 ρ=0.326 / g3 ρ=0.241 / g4 ρ=0.675，n=29/44/36），
   与本地配对数据（ρ=0.357）一致。偏差系数因候选而异（归一化比值区间
   0.614–2.545）。
3. **但选品几乎不变**，原因有二：
   - **最终 50 条的排序依据是（丢包率, 延迟）**，不是速度
     （`filter_clean` 按 `(loss_rate, avg_ms)` 排序后取 top_n）——速度从来
     没有参与过排序，换口径不改变排序依据；
   - 速度只通过共识的**相对**门槛 `T = 0.3 × 中位数` 影响淘汰，而该门槛在
     这三轮都**几乎没有绑定**（g2：A 淘汰 0 / B 淘汰 1，判定不一致 1；
     g3：A 淘汰 1 / B 淘汰 1，**判定不一致 0**；g4：A 淘汰 1 / B 淘汰 1，
     **判定不一致 0**）。
   - 所以「选品偏向低延迟而不是高带宽」这个担心是**伪问题**：选品一直就是按
     延迟/丢包挑的，速度只当门禁用。
   - ⚠️ **这个结论有前提**：`min_speed_mbps = 0`。若将来开了 `min_speed > 0`，
     `filter_clean` 会按速度门槛剔除，速度就**参与**选品了。已在
     `filter.py` 的 docstring 与 config 注释里写明。
4. **受影响的是「报告出来的速度数值」与「综合打分的速度分档」**：
   - `speed_mbps` 变成 256KB 段速率（已标注口径变更）；
   - `screener/score.py` 的速度分档是**绝对阈值**（>20 / >10 / >5 / >1 MB/s），
     在 256KB 口径下等效于「真实速率 >182 / >91 / >45 / >9 MB/s」——**比分档
     严格了约 9 倍**。故新增 `speed_scale`：把读数换算回 10MB 口径再分档
     （系数由 `speedtest.score_scale_for_url()` 按 `speed_url` 的体量自动查表：
     10MB→1.0、1MB→5.0、256KB→9.0）。
     - 影响范围：高分节点的基础分（60+延迟+丢包+TLS+colo+原生段）通常已把
       总分推过 100，clamp 之后速度项**看不见**——所以口径下移主要影响
       **慢节点/低质节点**（基础分不饱和的那些）的分数与分类。
     - **score 的绝对值仍不可跨版本比较**（口径变了）。

### 顺带修正一个此前的错误结论

我此前写「发起速率是次要因素」（(b) 10MB @4 req/s → 46% 429，而 1 req/s 的
(??) → 更少）。g2 的数据**推翻了它**：10MB @**1** req/s（需求字节率 10MB/s，
比 (b) 低 4 倍）反而被限 **88%**（263/300），比 (b) 的 46% 更差。
而 1MB @17 req/s（需求字节率 17MB/s）→ **0%** 429。

所以在 1–17 req/s 这个测试区间内，**决定因素是「单请求体量」（10MB 必被限、
1MB/256KB 从不被限），不是发起速率、也不是总字节/秒**。此前「≤17MB/s 不
触发、40MB/s 触发 46%」的阈值界定**不成立**（它把出口差异当成了速率效应），
应改为：**10MB 单请求必被限（46%–88%，随出口与累计量波动），≤1MB 不被限
（跨 4 个出口、1200+ 次请求 0 次 429）**。

默认体量 10MB → 256KB 是 40 倍缩小，`speed_mbps` 的含义随之从「10MB 全程
平均速率」变成「**256KB 段传输速率**」，**两者不可直接比较**。

### 偏差系数因候选而异 → 256KB 不是「整体缩放」

同 IP 配对（n=8 完整配对），以 10MB 为基准的**归一化比值**：

| 体量/基准 | 中位 | min | max | 标准差 |
| --- | --- | --- | --- | --- |
| 10MB/256KB | 1.055 | 0.914 | 1.729 | 0.249 |
| 1MB/256KB | 1.058 | 0.442 | 2.211 | 0.504 |

**偏差系数在候选间差 1.9 倍** → 256KB 口径不是「整体缩放」，而是**因候选
而异**，所以它会改变相对排序。

### 相对排序的一致性（决定「选品会不会变」的关键量）

- **Spearman 秩相关 10MB vs 256KB：ρ = 0.357**（n=8）——**弱相关**。
  1MB vs 256KB：ρ = 0.738，明显更好。
- 自选门槛 `T = 0.3 × 中位数` 下的淘汰判定：这 8 个样本在两种口径下
  **判定完全一致**（都淘汰 0 个）——因为它们的归一化值都远高于 0.3，
  离门槛边界很远。**真正会翻转的是那些恰好落在门槛附近的候选**，
  本样本里没有这种候选。
- 归一化值分布：10MB 口径 0.92–2.10，256KB 口径 0.82–1.21。

结论：**「256KB 会改变选品」这个担心，从本地配对数据看是成立的**（秩相关
只有 0.36、偏差系数因候选而异），但**证据强度不足**（n=8、单批候选，
且没有落在门槛边界的候选）。**必须在 CI 上用同批候选做双体量对照**才能
给出答案——分两次跑做不到（候选池每次重抓、内容会变），故新增
`--speed-compare-url` 模式：**同一批候选、同轮、同出口**再测一次另一种
体量，直接输出 Spearman、归一化比值区间与门槛判定差异。

### (f) 组的实际速率是「实测值」，不是推算值

(f) 组：300 + 272 + 272 = **844 个请求**，测速阶段 19:26:54.55 → 19:27:44.21
= **49.66s** → **实测 17.0 req/s**。

这个数**不是**「标称 4 req/s × 并发 8 = 32」推算来的——限速器有并发 bug
（并发等待者同时醒来同时发起），实际速率是**涌现**的，受下载耗时与信号量
回收速度约束。所以「需求字节率 ≤17MB/s 不触发限流」这个界定成立，依据是
**实测 844 请求 / 49.66s**，不是标称值。限速器已修（按绝对槽位排队），
修复后标称值才等于实际值——修完后 (f) 这组需要重跑才能对比。

### 偏差有多大：同 IP、同链路、交替测量的配对比值

在 ~200ms RTT 的链路上对同一批 IP 交替测三档体量（每档 2 次，取中位）：

| 体量 | n | min | 中位 | max | 相对 10MB |
| --- | --- | --- | --- | --- | --- |
| 256KB | 18 | 0.52 | **0.62** | 1.19 | **0.10** |
| 1MB | 18 | 0.52 | **1.19** | 3.28 | **0.20** |
| 10MB | 16 | 5.14 | **5.97** | 13.05 | 1.00 |

**配对比值 256KB/10MB：中位 0.10（min 0.06 / max 0.11）**——同一台机器、
同一条链路、同一个 IP，256KB 测出的速度只有 10MB 的 **约 1/10**。
1MB 比 256KB 好一倍（0.20），但仍差 5 倍。

机理：TCP 慢启动是指数增长，达到稳态要 ~10 个 RTT；256KB 在 200ms RTT 下
根本走不完慢启动，测到的是**爬坡段平均速率**而不是稳态速率。10MB 的前
1/10 是爬坡、后 9/10 是稳态，所以平均值接近真实速率。

> 附带证据：这次本地测量里 **10MB 请求有 2 次被 429**（`rate_limited`），
> 1MB 与 256KB 一次都没有。**字节型限流在本地住宅 IP 上同样复现**，
> 不只是 CI runner 的现象。

### 三个推论

1. **「50 条只是能连上」不成立**：CI 那 50 条的实测速度是 **26.4 – 72.7
   MB/s、中位 49.1**（256KB 口径），远高于担心的 0.5–2MB/s 区间。
2. **门槛不受影响**：`T = 0.3 × 首轮中位数` 是**相对**门槛，取本轮中位数的
   比例，不依赖绝对量级。体量变化不改变门槛的严格程度。
3. **但排序会受影响（真实风险）**：偏差系数 ≈ 慢启动爬坡字节 / 传输总量，
   它**随 RTT 变化**（RTT 越低偏差越小）。所以 256KB 口径下
   「低延迟节点」会被相对高估——它测的更像延迟而不是带宽。
   - CI 的 1.5ms RTT 下偏差温和（(d) 256KB 中位 49.1 vs (b) 10MB 中位
     123.3；但两组不是同批候选、不是同一时段、不是同一出口，只能当量级参考）；
   - **本地链路（~200ms RTT）偏差达 10×**——这正是项目文档里推荐的
     「本地二次筛选」场景，用 256KB 会严重失真。
   - 因此：**本地跑请显式用 10MB**：
     `python main.py --speed-url "https://speed.cloudflare.com/__down?bytes=10485760" --speed-rate-limit 1`
     （本地每个 10MB 下载要 2s，天然就是 ~0.5 req/s；限速器保证不越过
     字节型限流的阈值。）

### 体量选择是**视角相关**的，不是单一最优解

| 视角 | RTT | 建议体量 | 理由 |
| --- | --- | --- | --- |
| CI（美西 runner） | ~1.5ms | **256KB**（现状） | BDP 极小，爬坡占比小；且 707 次请求 0 次 429，无需限速；测速阶段 18s |
| 本地（中国住宅） | ~200ms | **10MB + `--speed-rate-limit 1`** | 256KB 会低估 10 倍；10MB 在 1 req/s 下需求字节率 ~10MB/s，不触限 |

这是物理约束（BDP）不是设计缺陷：**要让速度测量准确，传输量必须大到能走出
慢启动；而传输量大到 10MB 就会撞 CF 的字节型限流**。限速器正是让两者
共存的东西——它把「总字节/秒」压到阈值以下，于是可以用准确的体量。
（限速器原先有并发 bug：并发等待者同时醒来，实际速率 = rate × 并发。
已修成按绝对槽位排队，测试锁死间隔序列。）

### 备选方案：1MB + 限速

(f) 组：`--speed-url .../bytes=1048576 --speed-rate-limit 4`，300 候选 × 3 轮

- **429 = 0**（200×273 403×21 404×4 301×1）——1MB 单请求也没撞字节型限流；
- 测速阶段 50s 跑完 3 轮；
- 纯净 50/50 good；
- **收满门禁第一次真的触发**（剔除 1 条「200 但未收满请求体量」）——门禁
  有存在价值，且与体量无关。

即：**限流约束的是「总字节/秒」或「单请求体量」，1MB 在 4 req/s 下两者都
不触顶**。1MB 是比 256KB 更准的测量体量（爬坡占比更小），代价是每次多传
0.75MB、限速后耗时更长。最终选型见下节。

## 跑实验前的核对清单（两次踩坑换来的）

1. **推送后必须逐项核对 remote**：`git ls-remote origin main` 的 SHA
   是否等于本地 HEAD；`git show origin/main:config.py | grep speed_url`
   是否是你要的默认值；`git cat-file -s origin/main:result/clean-ips.txt`
   的字节数是否符合预期。
   - 踩坑记录：CI 的自动提交与我的 push 撞车，push 被拒而我没核对，
     导致「最终验证」跑在**旧 10MB 配置**上（429×240、纯净 0）——
     差点让「0 次 429」的结论建立在错误数据上。
2. **`extra_args` 不要加引号**：bash 的**引号移除不作用于参数展开的结果**，
   引号是字面量 → URL 变成 `"https://..."`（带引号字符）→ 主机名解析失败
   → 首轮 400×49 / connect 79。
   - 踩坑记录：第一次跑 (c) 的数据**全部作废**。这个坑的真正危险不在于坑
     本身，而在于**它的现象与「限流」几乎一样**——如果当时没发现，结论会
     变成「256KB 也不行」，方向完全错。
3. **看日志里的目标 URL**：确认 `目标 https://...bytes=NNNNNN` 里的数字是
   你要的体量，别信命令行的写法。

## 顺带修掉的一个坑

第一次跑 (c) 时在 `extra_args` 里写了带引号的 URL
（`--speed-url "https://...262144"`）。bash 的**引号移除不作用于参数展开的
结果**，引号是字面量 → URL 变成 `"https://...262144"` → 主机名解析失败 →
首轮 400×49 / connect 79。现象极像「限流」，差点误判成「256KB 也不行」。
修法：工作流在拼接前 `tr -d '"'` 去掉引号，并在输入框说明里写明不要加引号。

## 复现方式

在 Actions 里手动触发 `定时筛选纯净IP`，`extra_args` 填（**不要加引号**）：

```
(a) --limit 150 --speed-rounds 1 --speed-url https://speed.cloudflare.com/__down?bytes=10485760
(b) --limit 150 --speed-rounds 1 --speed-rate-limit 2 --speed-concurrency 2 --speed-url https://speed.cloudflare.com/__down?bytes=10485760
(c) --limit 150 --speed-rounds 1 --speed-url https://speed.cloudflare.com/__down?bytes=262144
(d) --speed-url https://speed.cloudflare.com/__down?bytes=262144
```

每组必记：首轮 HTTP 状态码 / 首轮失败归因 / **在飞下载峰值** / **出口 IP** /
收满门禁剔除数 / 纯净数。出口 IP 必须记——不同出口的配额不同，比例不可跨
出口比较（本次 (c)(d)(e) 用了三个不同出口，但都是 0% 429，方向可复现）。

## 附：本地 10MB 的 429 是「逐边缘 + 体量驱动」（2026-10-22）

背景：按「本地跑用 10MB + `--speed-rate-limit 1`」跑了一次完整扫描
（`local-runs/2026-10-22_2205-evening`，并发 1；耗时 20 分钟，测速阶段
296 次请求 ≈ 0.43 req/s，**低于**限速器 1 req/s 上限），结果
`429×208 / 296`（70%），最终只剩 4 条。四个对照（同一时刻、同一批 IP）：

| 对照 | 结果 |
| --- | --- |
| 本机直连最近边缘 `speed.cloudflare.com`，**10MB** | **6/6 = 200**（19–55s/次） |
| 运行里拿到 429 的 4 个候选 IP，**10MB** | **4/4 = 429** |
| 同样这 4 个 IP，**256KB** | **4/4 = 200**（1.45–1.74 MB/s） |
| 同样这 4 个 IP，普通域名 `www.cloudflare.com` | **4/4 = 200**（colo NRT） |

→ 429 既不是「本机出口被限」（直连最近边缘 10MB 全 200），也不是「边缘不服务
测速端点」（普通域名全 200、**换小体量立刻 200**），而是**该边缘对大体量请求
的拒绝**。且**跨时间稳定**：跑完 23 分钟后再测，429 的仍 429、200 的仍 200
（1/1 复测）——不是抖动，重试救不回来。

推论（对本地攒库的直接影响）：**不是「产出 ~30%」——30% 只是非 429 率**。
296 个候选里真正通过（非 429 + 速度/共识达标）的只有 **4 条 = 1.3%**，其余
88 条非 429 里大部分速度也不达标。所以 10MB 手扫每轮的产出一律是个位数，
4 轮样本（去重后约 10 条）算留存率的置信区间宽到没有决策价值。

**决定（2026-10-22）：放弃「留存率验证」，改成「积累」。** 不追求统计显著性：

- 每次 10MB 跑完，把 `clean-ips.txt` 逐行加日期前缀追加到
  `local-lib/passed-ips.log`（`local-lib/` 与 `local-runs/` 都不入库）；
- 攒 ~10 次后人工数出现次数：出现 ≥5 次的 IP 就是「本机网络上稳定可用」的，
  直接当本地库；没有重复出现 → 说明波动大，本地库不值得建；
- **不用 256KB 替代**：256KB 的通过率接近 100%（本轮 429 的 4 个 IP 换
  256KB 全 200），「可用性留存」没有区分度；而 10MB 有区分度但样本小。
  当前网络条件下拿不到「大样本 + 准速度」——这是条件限制，不是方案问题。
- 追加时**显式指定编码**（PowerShell 5.1 的 `Get-Content`/`Add-Content`
  默认按 ANSI 读写，中文标签会变乱码；IP 不受影响，但以后人工看会看不懂）：

  ```powershell
  Get-Content .\local-runs\<目录>\clean-ips.txt -Encoding UTF8 |
    ForEach-Object { "$(Get-Date -Format 'yyyy-MM-dd') $_" } |
    Add-Content .\local-lib\passed-ips.log -Encoding UTF8
  ```
